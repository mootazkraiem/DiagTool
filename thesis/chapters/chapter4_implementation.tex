\chapter{Implementation}
\label{chap:impl}

\section{Introduction}

This chapter describes how the design presented in Chapter~\ref{chap:design} was implemented. It covers the development environment, the desktop application, the backend, the replay engine and parsers, the \gls{mf4} conversion path, the vehicle profile system, the \gls{ai} explanation module, the charting and export features, the settings module, and the hardware layer. The machine-learning pipeline itself is covered in Chapter~\ref{chap:design}, since that design work was carried out before this implementation phase; this chapter shows how the runtime engine uses it, without repeating the algorithm discussion. Only short, illustrative snippets are shown, full listings are not included, in line with the reporting guidelines followed for this document.

\section{Development environment}

\begin{itemize}
    \item \textbf{Hardware.} A standard Windows desktop/laptop workstation was used for development, training, and validation; no specialized hardware was required for the software work. The live hardware capture path targets an ELM327 (serial/slcan), a PEAK PCAN-USB adapter, or native SocketCAN, but validating this path end to end requires a physical vehicle to connect it to, and no compatible electric vehicle was available during the project (Chapter~\ref{chap:validation}, Limitations).
    \item \textbf{Operating system.} Windows 10/11, the target platform for the \gls{wpf} desktop client.
    \item \textbf{Languages.} C\# (.NET Framework 4.8) for the desktop client, Python for the backend.
    \item \textbf{Key libraries.} \gls{wpf} and CommunityToolkit.Mvvm for the client, FastAPI and uvicorn for the \gls{rest} \gls{api}, scikit-learn~\cite{pedregosa2011scikit} for Isolation Forest and K-Means, pandas and \texttt{asammdf} for data processing and \gls{mf4} decoding~\cite{asam_mdf}, \texttt{python-can} for the hardware layer, PDFsharp for PDF export.
    \item \textbf{Tooling.} Visual Studio for the C\# client, a standard Python virtual environment for the backend, SQLite as the embedded database, requiring no separate server process.
\end{itemize}

\section{WPF application}

The desktop client is a WPF application targeting .NET Framework 4.8, structured with the \gls{mvvm} pattern. Its purpose is to give the analyst one place to import a log, replay it, watch live traffic, review alerts, and export a report. The main window hosts a navigation bar (Home, Dashboard, Telemetry, Diagnostics, Log Playback, Settings, Anomaly Intel), with each section built as a self-contained view bound to its own view-model.

Two shared services sit behind every screen: an \gls{api} client that wraps every backend call behind a typed method, and a data service that holds the client-side state shared across views (the current snapshot, the alert history, and replay or live runtime metrics), polling the backend periodically and notifying the screens when something changes.

\section{FastAPI backend}

The backend entry point defines all \gls{rest} endpoints in a single FastAPI~\cite{fastapi} application. Long-running operations, such as starting a replay or running an offline batch analysis, are launched as a subprocess or background thread, and the endpoint returns immediately with a status the client can poll. Shared, process-lifetime state (the current replay process handle, the most recent alert context list, the explanation cache) is protected by explicit locks where it is shared between the request-handling thread and a background monitoring thread.

\subsection{Replay engine}
\label{sec:impl-replay}

This section describes the concrete implementation of the replay engine introduced in Section~\ref{sec:design-replay}. It is invoked as a subprocess by the replay-start endpoint. It loads the input file through the shared, format-aware loader described in Section~\ref{sec:impl-parser}, builds three aligned arrays (timestamps, identifiers, payloads), and feeds them one by one into the runtime detection engine, configured with the requested vehicle identifier. Every 1{,}000 frames it writes a partial-alerts file to disk so the client can show live progress before the run completes; at the end it writes a summary file containing the full alert list and per-run statistics, which the client reads to display results.

A background thread on the server side waits for the subprocess to exit and updates the replay status to completed or error. It also publishes this replay's own alerts into the state consumed by the \gls{ai} explanation endpoint, a step added during the validation phase described in Chapter~\ref{chap:validation}.

\subsection{Parser and canonical frame representation}
\label{sec:impl-parser}

Every supported log format is converted, at import time, into the same canonical stream: a sequence of timestamp, identifier, and payload tuples. A single dispatch function selects the correct parser by file extension:

\begin{itemize}
    \item \textbf{.csv} --- generic timestamp/identifier/byte columns, or SavvyCAN-style columns.
    \item \textbf{.mf4} --- ASAM \gls{mf4}~\cite{asam_mdf} binary logs, decoded with \texttt{asammdf} (Section~\ref{sec:impl-mf4}).
    \item \textbf{.asc} --- Vector \gls{can} text format.
    \item \textbf{.log} --- candump / SocketCAN text format, including the timestamped variant used by several public datasets.
    \item \textbf{.txt} --- PCAN text format, falling back to candump parsing if the PCAN pattern is not matched.
\end{itemize}

This single dispatch point is what both the replay engine and the offline batch analyzer call, so that a defect in one format's parser cannot silently produce a different frame stream for replay than for offline analysis. Chapter~\ref{chap:validation} documents a defect found in exactly this area: before the fix, the replay engine had its own, separate, \gls{csv}-only loading code that ignored this shared dispatcher.

\subsection{MF4 conversion}
\label{sec:impl-mf4}

\gls{mf4} files recorded by multi-channel CANedge-style loggers can spread real \gls{can} traffic across several channel groups, most of which are empty template groups. The conversion code iterates every group in the file explicitly and merges the populated ones, instead of relying on the library's default single-dataframe view, which only surfaces the first group and silently drops the rest. This function is shared between the standalone \gls{mf4}-to-\gls{csv} conversion tool and the format-aware parser described above, so both code paths see the same, complete set of frames.

\section{AI explanation module}

The explanation module implements the workflow introduced in Section~\ref{sec:design-ai}, and is called from the explanation endpoint. It builds a context object from four sources: the alert's own features, expected statistics for the current vehicle state, a keyword match against a small attack knowledge base, and the most similar past anomaly retrieved by cosine similarity from a persistent history store.

This context is then sent to a provider chain that tries Google Gemini first, then a locally running Ollama model, and finally a rule-based template. The template fills in the same fields (summary, detail, recommendation) directly from the numeric context, so an explanation is always produced even with no network access. Each resolved explanation is also appended to the historical anomaly store, so that later, similar anomalies can reference it.

Explanations are cached by a key derived from the alert's own identifier and score, to avoid asking the language model the same question twice for the same alert within a run. Chapter~\ref{chap:validation} documents how the lifecycle of this cache, not the explanation logic itself, was the source of a validation defect, and how it was corrected.

\section{Charts}

The client draws its charts (anomaly score history, per-identifier activity, severity distribution, live signal channels) directly with native WPF drawing primitives bound to rolling data buffers updated on each tick, rather than a third-party charting library, keeping the rendering path simple and dependency-free.

\section{Export}

Two export paths are implemented from the Anomaly Intel view, shown in Figure~\ref{fig:export-workflow}: \gls{csv} export writes the currently displayed alert list, including the parsed reason, knowledge-base match label, and explanation text where available, to a user-chosen file; PDF export, built on PDFsharp, renders a paginated A4 report with a header, summary statistics, and a formatted alert table, suitable for sharing outside the application. Both paths read from the same in-memory alert list the analyst is looking at, so an export always matches what is currently on screen.

\section{Settings}

The Settings view lets the analyst configure the alert threshold, the \gls{llm} provider key (Gemini), and the hardware interface (adapter type, COM port, bit rate). Configuration is persisted locally and reloaded on startup, and any configured \gls{llm} key is applied automatically so the backend picks it up without a separate configuration step.

\section{Hardware}

The hardware module wraps \texttt{python-can} to support ELM327 (over an slcan serial connection), PEAK PCAN-USB, and native SocketCAN. Connecting sets the engine's active vehicle identifier, so live frames are scored with the correct per-vehicle model, exactly as a replay does. Disconnecting resets it to the generic profile, so a later, unrelated request does not keep scoring against a vehicle that is no longer connected.

\section{Conclusion}

This chapter described the implementation of CANvisionNative's main modules: the development environment, the WPF client and its two shared services, the FastAPI backend and its replay engine, the shared canonical parser and \gls{mf4} conversion path, the vehicle profile system, the \gls{ai} explanation module, and the charting, export, settings, and hardware layers. The machine-learning approach these modules build on is presented in Chapter~\ref{chap:design}, since that work was carried out before this implementation phase. The next chapter presents how this implementation was validated against a real vehicle recording, the defects found, and the corrections applied.
